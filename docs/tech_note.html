Sim3dViewのしくみ

C++は書けるけれど、Rust・Web・WebAssembly・GPU描画はまったく触ったことがない—— そんなあなたのために、このプロジェクトで使われている技術を土台から積み上げて説明します。 C++との対比を手すりにしながら読み進めれば、最後には自分のコードが読めるようになるはずです。

2つ前の版で変わったこと(覆域データの平滑化を撤去)
  • 覆域(3Dドーム・2D領域)の平滑化を、撤去しました。「覆域データの平滑化はやっぱりやめにしたい」という要望を受け、方位ごとの半径をなだらかにしていたメディアン→平均(ドームは仰角方向の平均も)を取りやめ、 DomeRing・LosPointの生の計算結果をそのまま頂点に使うようにしました。地形の細かい凹凸や1方位だけの遮蔽が作る放射状の筋(ドーム)、低い高度での境界のギザギザ(2D覆域)は、平滑化する前の見え方に戻ります(36.2・36.3・36.6節)。
  • 平滑化以外の対策は、そのまま残っています。半径の丸め誤差の修正、リング数・間引き、覆域の計算の小分け・キャッシュ・複数覆域の同時表示は変更していません。
  • 節番号は変わっていません。36.2・36.3・36.5・36.6節の記述を、平滑化を撤去した現状に合わせて書き換えています。
3つ前の版で変わったこと(3Dモデル(glTF)の表示)
  • 航跡を、glTF(GLB)の3Dモデルで表示できるようになりました。UnityやBlenderで作ったモデルを、GLB形式で書き出して地図に置けます(FBXは対応しないので、Blenderなどでglbへ変換します)。 種別(航空機・ヘリ・艦船・車両・ミサイル)ごとに使うモデルのURLをModelsStateへ登録するだけです(38.8節)。
  • 表示方式は3つ。「近くはモデル・遠くはシンボル」(既定。カメラからの距離で入れ替える)、「常にモデル(最小サイズを保証)」(小さくなりすぎるモデルは実寸より大きくして、画面で最低のpxを保つ)、「シンボルのみ」。 表示メニューの「3Dモデル...」の移動できるウインドウで切り替えます。
  • 向きは、ヘディングに加えてピッチ・ロールも反映します。ピッチ・ロールはサーバー(C++)がTrackListに載せて送ります(デモは、旋回のバンク・上昇降下・艦船の波の揺れ)。地球の丸みで傾く「地点の上」にも沿います。
  • おまけ機能として、既存の描画から切り離して作りました。純粋な計算(terrain::models)・GPU(renderer/model_batch.rs+model.wgsl)・組み込み(ui/terrain_view/models.rs)に閉じ、 既存のコードへの変更はTrackのピッチ・ロール、シンボルを描かない指定、地点の東・北・上を返す関数、描画のフック数か所だけです。テクスチャ・アニメーションは対応しません。
  • サンプルのモデル(航空機・ヘリ・艦船・車両・ミサイルの簡易な低ポリゴン)は、scripts/gen_sample_models.pyが標準ライブラリだけで生成します。
  • 節番号は変わっていません。新しい内容は38.8節にあり、38.2・38.4節のプロトコルとコードの抜粋にピッチ・ロールを足しています。
3つ前の版で変わったこと(複数の覆域の同時表示・選択したシンボル中心の断面図・シンボルの埋まり・LODのクロスフェード・覆域の軽量化と平滑化)
  • 複数の覆域を、同時に表示できるようになりました。見通し範囲タブの「すべての観測点の覆域を同時に表示」をONにすると、すべての観測点の3Dドーム・2D領域が同時に出ます。観測点ごとに色が違い、計算・キャッシュ・頂点も観測点ごとに独立です(36.7節)。
  • 断面図が、選択したシンボルを中心に表示されるようになりました。地図でシンボルを選択すると、その位置を中心(距離0)に、方位角の直線の両側の断面を出します。何も選択していなければ基準位置が中心です。シンボルの高度の位置に印が付き、「進行方向」ボタンで方位角をシンボルの向きに合わせられます。シンボルは毎秒何度も動くので、断面の再計算は約500m動いたときだけです(27.3節)。
  • 高度0m付近のシンボルが、地面や水面に埋まらなくなりました。カメラを浅い角度に倒すと、地面すれすれの船や車両のシンボルの下半分が、手前の地形・水面に隠れていました。 原因はビルボードの深度が足元1点で一定だったこと。いまは、その画素の視線が地面に当たる点の深度まで手前へ寄せます(36.4節)。
  • 地形のレベルの切り替えが、なめらかになりました。チャンクのレベルが変わるとき、古いメッシュを350ms残し、新旧を画素ごとのディザで補い合う割合で重ねて描きます(クロスフェード)。 細かさ・陰影の違いが一瞬で切り替わって境目が目立つのを、時間をかけて混ぜて和らげます(14.11節)。
  • 覆域を出したままの操作が、重くなくなりました。ズームのたびに約1秒ずつ固まっていたのを、計算の小分け(非同期)・キャッシュ・方位の間引きで、約70msまで減らしました(36.5節)。 あわせてドームの平滑化を、方位方向に加えて仰角方向にも入れ、高いリングほど頂点を間引いて、頂点数も約71万→約16万にしました(36.2節)。
  • 遠方の地形が、より細かくなりました。レベル選択の目標を「1セル1ピクセル以下」から0.7ピクセル以下にし、頂点の予算はレベルごとの周回(全チャンクをL2まで→L3まで→…)で配る方式にしました(14.2・14.3・14.9節)。
  • 2D覆域も平滑化しました。低い高度(たとえば50m)で、島や岩の陰が細い楔になって境界がギザギザになるのを、ドームと同じ角度の幅(メディアン±2・平均±6を2回)でなだらかにしました(36.3節の末尾)。
  • 平滑化の方法を、まとめて解説しました(メディアン→平均を重ねる理由、リング方向、窓幅を角度で揃える、平滑化しても変わらないもの。36.6節)。
  • 節番号は変わっていません。新しい内容は、14.11・27.3の末尾・36.4〜36.7の各小節と36.3節の末尾にあり、14.2・14.3・14.9・36.1・36.2・13節の該当箇所を直しています。

7つ前の版で変わったこと(地形の表示の高速化)
  • 地形が、地図の品質を変えずに速く出るようになりました。ページを開いてから俯瞰の見た目が整うまでが、約6.8秒→約2.9秒(同じPC上のサーバー、実測)。全タイルのL1の取得が終わるのは5.3秒→2.2秒です(14.4・14.9節)。
  • 原因は通信ではなくスケジューリングでした。1件の取得は中央値11msなのに、取得の補充が150msのデバウンス経由(16件が約0.19秒周期)、メッシュ反映が「1回60万頂点+150ms待ち」で、別々の下限を作っていました。両方を直し、反映の区切りは頂点数から時間の目安(12ms)にしました。
  • サーバーが地形にETag+Cache-Control: no-cacheを付け、2回目以降は304で済みます(L1の転送量25.8MB→0.1MB。7節・14.5節)。有効期限は付けないので、map_data/を作り直せば必ず新しくなります。

2 WebAssembly(WASM)とは何か

「Rustのコードがブラウザで動く」の正体がWebAssemblyです。

WebAssemblyは、CPUの機械語ではなくブラウザが実行できる、コンパクトでポータブルなバイナリ形式です。 C++で言えば「x86_64向けにビルドした実行ファイル」の代わりに「WASM向けにビルドしたバイナリ」を作るイメージに近く、 実際 rustc(RustのコンパイラでLLVMベース、C++のclangと同じ系統)に --target wasm32-unknown-unknown を指定するだけで、同じRustコードから Windows用exeの代わりにWASMバイナリを吐き出せます。

💡 ここが面白いところ

WASMは「サンドボックス化された仮想CPU」のようなもので、メモリ破壊があってもブラウザ全体は壊れません。 その代わり、ファイルシステムやソケットに直接アクセスできず、必ずbrowserが提供するAPI(fetch、 WebSocket、Canvasなど)経由で外の世界とやり取りします。 web_sysクレートはこれらのAPIのRustバインディングです。

3.1 所有権と借用 — Rust最大の壁にして最大の武器

Rustの一番の特徴は「すべての値には所有者(owner)が1人だけいる」というルールです。 C++で生ポインタを2箇所に持たせてどちらが解放するか曖昧になる、という事故が、Rustではコンパイルエラーになります。 

rust — 所有権の基本fn main() {
    let s1 = String::from("origin"); // s1がこの文字列を所有
    let s2 = s1;                     // 所有権がs2へ move
    // println!("{s1}");             // ← コンパイルエラー! s1はもう使えない

    let s3 = String::from("origin");
    print_len(&s3);                  // &s3 = 借用。所有権は動かない
    println!("{s3}");              // なのでs3はまだ使える
}

fn print_len(s: &String) {       // C++でいう const std::string&
    println!("{}", s.len());
}
🔧 C++erの視点

「move」はC++11のstd::moveと全く同じ概念です。違いは、C++では move後の値を使ってもコンパイラは黙って未定義動作を許しますが、Rustは コンパイルエラーで止めてくれる点です。Sim3dViewの WsConnection(ws.rs)がRc<RefCell<Inner>>を 抱えているのは、複数のクロージャから同じ接続状態を「共有所有」したいからで、C++の shared_ptr<Inner>+ 自前ロックに相当します。

3.2 enumとOption/Result — 「ありえない状態」を型で消す

RustのenumはC++のenum classより強力で、各バリアントにデータを持たせられます。 これは実質「タグ付きunion」で、C++で言うとstd::variantに近いですが、パターンマッチ (match)で網羅チェックがコンパイル時に強制されます。 

sample/sim_frontend/src/ws.rs（実際のコード）pub enum ConnectionStatus {
    Connecting,
    Connected,
    Reconnecting { attempt: u32 },  // このバリアントだけ数値を持つ
    PausedHidden,
}

これを使う側はmatchで全パターンを尽くさないとコンパイルが通りません。 「新しい状態を追加したのに一部の処理漏れがある」というC++のswitchで起きがちなバグを コンパイラが検出してくれます。

Option<T>とResult<T, E>もenumの一種です: 

enum Option<T> { Some(T), None }
enum Result<T, E> { Ok(T), Err(E) }

「値があるかもしれない/ないかもしれない」「成功するかもしれない/失敗するかもしれない」を 戻り値の型そのもので表現するので、呼び出し側はコンパイラに強制されて必ず 両方のケースを処理することになります。?演算子は「エラーなら即座に呼び出し元へ return する」糖衣構文で、Sim3dViewのfetch.rs(HTTPでの取得)で多用されています。 

sim3dview/src/terrain/fetch.rs（実際のコード、抜粋）pub async fn fetch_metadata(base_url: &str) -> Result<TerrainMetadata, String> {
    gloo_net::http::Request::get(&format!("{base_url}/metadata.json"))
        .send().await
        .map_err(|e| format!("metadata.json fetch failed: {e}"))?  // 失敗ならここでreturn
        .json().await
        .map_err(|e| format!("metadata.json parse failed: {e}"))
}

base_urlは引数で受け取ります。ライブラリは「どのサーバーから取るか」を決めず、 呼び出し側(アプリ)が渡す作りになっています(6節)。

3.3 trait — C++のConceptsに一番近い

traitは「この型はこういうメソッドを持つ」という契約です。C++20のconceptや、 継承ベースの抽象基底クラスに近い役割を果たしますが、既存の型に後から実装を追加できる点が違います。 Sim3dViewでは#[derive(Clone, Copy, bytemuck::Pod, bytemuck::Zeroable)]のように 「このstructに対して自動でtraitを実装してください」というderiveマクロを多用しています (Pod/Zeroableは「このメモリレイアウトはGPUバッファへそのままコピーしてよい」 という保証をコンパイラに与えるtraitです)。

4 Leptos: リアクティブUIという考え方

Leptosは「状態(Signal)が変わったら、画面のうちその状態に依存する部分だけが自動で再計算される」 フレームワークです。DOMを手で書き換えるコードは(ほぼ)出てきません。

Sim3dViewのWsSignals構造体(実際のコード)は、この「状態の入れ物」を1箇所にまとめたものです: 

sample/sim_frontend/src/ws.rs（実際のコード）#[derive(Clone, Copy)]
pub struct WsSignals {
    pub status: RwSignal<ConnectionStatus>,
    pub origin: RwSignal<Option<OriginState>>,
    pub vab_config: RwSignal<Option<VabConfig>>,
    pub status_panel_config: RwSignal<Option<StatusPanelConfig>>,
    pub last_sim_state: RwSignal<Option<SimState>>,
    pub last_command_error: RwSignal<Option<CommandError>>,
    pub app_status: RwSignal<Option<AppStatus>>,  // 「実行中/一時停止中」の表示文字列
}

RwSignal<T>は「読み書きできる状態の入れ物」で、C++にたとえるなら std::atomic<T>に「値が変わったら登録されたコールバックを全部呼ぶ」機能を足したもの、 とイメージすると近いです(実際は内部的にRc参照カウント+インデックスで実装されています)。

コンポーネント(画面の部品)は、Rustの関数として書きます。#[component]属性を付けた関数が 1つの部品に対応し、view!マクロの中にHTMLに似た構文でUIを書きます:

sample/sim_frontend/src/components/vab.rs（実際のコード、抜粋）#[component]
pub fn VabPanel(conn: WsHandle) -> impl IntoView {
    let signals = use_context::<WsSignals>().expect("WsSignals context not found");

    view! {
        <div class="panel-section vab-panel">
            <h2>"VABパネル"</h2>
            {move || {
                // signals.vab_config が変化するたびに、この中身だけ再計算される
                let Some(cfg) = signals.vab_config.get() else {
                    return view! { <p class="placeholder">"(未受信)"</p> }.into_any();
                };
                // ...ボタン一覧を生成...
            }}
        </div>
    }
}

use_context::<T>()はDI(依存性注入)コンテナのようなものです。 親コンポーネント(App)がprovide_context(signals)で登録した値を、 子孫のどのコンポーネントからでも型で引き当てて取り出せます。 グローバル変数を使わずに「アプリ全体で共有したい状態」を配れる仕組みです。 sim3dviewライブラリも、この仕組みを「組み込みの窓口」にしています (TerrainStore・OriginState・RadarMarkersStateなどを アプリがprovide_contextすると、ライブラリの部品がそれを読む。6節)。

🔧 C++erの視点

Sendは「別のスレッドへ渡してよい」という印です。Leptosのview!の子は、サーバー側の描画(別スレッド)と共通のAPIなので、それを要求します。 ブラウザのWASMは単一スレッドなので、以前はunsafe impl Sendで「実際には安全」と約束していました。 StoredValue::new_localは、その約束をコンパイラに検査させる形です。値そのものは作ったスレッド専用の置き場にあり、渡すのはその場所を指す小さなハンドル(C++でいう、スレッドに固定されたthread_localな実体と、それを指す整数ID)だけです。 別のスレッドから触れば実行時に止まるので、unsafeで嘘をつくより安全です。

なぜ「1枚の画像」をやめたのか

以前の前処理は、全タイルを1枚の巨大な画像に敷き詰めて2048×2048へ縮小し、 1つのメッシュとして描いていました。入力のmap_data/が増えて、対象域が30度四方(390タイル、DSM合計約10GB)になると、 この方式は3か所で限界を迎えました。

限界数字
解像度が粗い30度 ÷ 2048 ≒ 1セル約1.6km(当初の5度四方なら約271mだった)。海岸線がギザギザに見える

そこで発想を変えました。「全部を細かく持つ」のをやめ、「見ている所だけ細かくする」。 3Dゲームの地形でおなじみのLOD(Level of Detail)です。その土台になるデータの作り方が、この節の内容です。 描画側の仕組みは14節で説明します。

5つの解像度レベル

1度×1度のタイルを、一辺Nセルに分けた(N+1)×(N+1)個のノードで表します。 Nが大きいほど細かく、レベル4の3600は元データの1画素=1セルです。 各ノードの値は、その位置を中心とする1セル幅の窓の中の有効画素の平均です(NaNは除外。窓に陸が1画素でもあれば陸、全部NaNなら海)。

チャンク: 1度タイルを6×6に切る

L4を1タイル分そのまま持つと、3601×3601 ≒ 1300万頂点(頂点バッファだけで約310MB)になり、 1枚のバッファの上限を超えます。しかも、カメラのすぐ近くの狭い範囲しか細かさは要りません。 そこでレベル1以上は、1度タイルを6×6=36個のチャンク(緯度経度とも1/6度、約18km×15km)に分け、 チャンクごとにグリッドを持ちます。最細のチャンクは1個で約36万頂点なので、近くの数個だけを30mにできます。

  • チャンクは縁のノードを隣と共有します(チャンクごとに(c+1)²ノード、c=N/6)。同じレベルどうしなら継ぎ目の高さが一致します
  • ファイルには、チャンクを行(南→北)・列(西→東)の順に、同じ大きさのレコードとして連結します。チャンク番号kのバイト位置は k × (c+1)² × 2 と計算で決まるので、 サーバーがHTTP Rangeに対応していれば、必要なチャンク1個分(L4で約0.7MB)だけを取得できます

void write_chunked_level_file(const fs::path& path, const std::vector<int16_t>& grid, int cells) {
    const int nodes = cells + 1;
    const int chunk_cells = cells / kChunksPerTile;
    std::vector<int16_t> record(static_cast<size_t>(chunk_cells + 1) * (chunk_cells + 1));
    for (int cy = 0; cy < kChunksPerTile; ++cy) {
        for (int cx = 0; cx < kChunksPerTile; ++cx) {
            for (int j = 0; j <= chunk_cells; ++j) {
                const int16_t* src = grid.data() + (cy * chunk_cells + j) * nodes + cx * chunk_cells;
                std::copy(src, src + chunk_cells + 1, record.begin() + j * (chunk_cells + 1));
            }
            out.write(reinterpret_cast<const char*>(record.data()), record.size() * sizeof(int16_t));
        }
    }
}

海は「データなし」で表し、三角形を張らない

10 座標変換(ENU)を図解する

「緯度・経度・標高」を「メートル単位のXYZ」に変換する部分です。地味ですが、このプロジェクトで 一番"応用数学"らしい箇所です。

地球は丸いので、緯度経度をそのままメートルとして扱うことはできません。そこでSim3dViewは、 ユーザーが指定した1点(原点)を基準に、そこだけをまっすぐな平面とみなす 近似(局所ENU座標系)を使います。

変換は2段階です。まず緯度経度標高を、地球の中心を原点とする3次元直交座標ECEF (Earth-Centered, Earth-Fixed)に変換し、次にECEF上で原点との差分を取って回転させ、 東西・南北・上下の3軸に射影します。

sim3dview/src/terrain/geodesy.rs（実際のコード、抜粋）fn geodetic_to_ecef(lat: f64, lon: f64, h: f64, a: f64, e2: f64) -> (f64, f64, f64) {
    let n = a / (1.0 - e2 * lat.sin().powi(2)).sqrt();
    let x = (n + h) * lat.cos() * lon.cos();
    let y = (n + h) * lat.cos() * lon.sin();
    let z = (n * (1.0 - e2) + h) * lat.sin();
    (x, y, z)
}

// EnuTransform::new: 原点の緯度経度から、ECEFの差分→ENUの回転行列を1回だけ作る(行が東・北・上)
let enu_from_ecef = DMat3::from_cols(
    DVec3::new(-sin_lon0, -sin_lat0 * cos_lon0, cos_lat0 * cos_lon0),
    DVec3::new( cos_lon0, -sin_lat0 * sin_lon0, cos_lat0 * sin_lon0),
    DVec3::new(0.0,       cos_lat0,             sin_lat0),
);
// EnuTransform::ecef_to_enu: 原点との差を東・北・上へ回転する(以前は3か所に同じ式がコピーされていた)
let [east, north, up] = (self.enu_from_ecef * (DVec3::new(x, y, z) - self.origin_ecef)).to_array();
[east as f32, north as f32, up as f32]   // 計算はf64、GPUへ渡す値だけf32へ

EnuTransformには逆向きのinverseもあります。原点からの東・北のオフセット(m)から 緯度経度を求める近似(原点の緯度での子午線・卯酉線の曲率半径を使う局所近似)で、断面図や見通し計算で 「原点から方位角の方向へ地表をたどる」ときに使います。

ただしinverseは原点の近くだけで成り立つ近似です。原点から数百km以上離れると、丸みの分だけ数十kmずれます。 遠方の地点には、ENU→ECEF→測地座標を反復法で解く厳密な逆変換enu_to_geodeticを使います(クリック位置の計算など。15節)。

💡 なぜフロント側(Rust)で計算するのか

原点はユーザーがUIから自由に指定できます。もし前処理(GDAL)側で座標変換までやってしまうと、 原点を変えるたびに前処理をやり直す必要があり非現実的です。そこで前処理は 「緯度経度のグリッド」のまま出力し、原点に依存する変換だけをフロント側が実行時に行う—— という役割分担にしています。原点が変わったら、常駐している全メッシュ(合計で最大約2,500万頂点。14節)の変換をやり直して、 頂点バッファを更新します。行(緯度)・列(経度)ごとの三角関数を前計算してあるので、1頂点あたりは数回の掛け算で済みます。

最後にf32へ落とすのも、原点基準にしておく理由の一つです。地球中心座標(値が約640万m)のまま f32にすると、表せる刻みは約0.5mに粗くなってしまいますが、原点からの東西南北の距離なら ずっと細かく表せます。

1枚のメッシュから、たくさんのメッシュへ

標高のグリッド(隣り合う4ノードごとに三角形を2枚)から、地形の「網」(メッシュ)を作ります。データなし(海)のノードを含む三角形は作りません。 1頂点は28バイト(位置12+色12+法線4)で、頂点バッファとインデックス(u32)を、メッシュ1個ごとにGPUへ上げておきます。 メッシュは、全タイルの下限(L1、約1,520万頂点)と、カメラに近いチャンクを細かくした分(約980万頂点)で、常駐の合計は最大でおよそ2,500万頂点です(14節)。 あとはカメラが動くたびにview_proj行列(視点+レンズの情報を1つの4×4行列にまとめたもの)などのuniformだけを送り直せば、 GPUが毎フレーム頂点を変換して描き直してくれます。

以前は「2048×2048の1枚のメッシュ(約419万頂点)を丸ごとGPUへ」でした。この方式では、解像度を上げると1つのバッファが WebGPUの上限(既定256MB)を超えてしまうため、地形LODに作り替えました。メッシュの作り方は、縁のスカート(14節)を含めて mesh.rsのgrid_vertices/grid_indicesが、タイル全体とチャンクで共通に使います。 全タイルを常駐させると画面の外の頂点が大量になるので、視錐台の外のメッシュは描きません(14.10)。

1枚の絵になるまで: 2倍の大きさで描いて、縮める

遠景では、細かい三角形が1画素に収まりきらず、斑点やちらつき(エイリアシング)が出ました。 対策は2段構えです。まず画面の2倍の解像度のテクスチャへ4倍MSAA付きで描き、 それを線形フィルタで実際のcanvasの大きさに縮めます。

③の「画面いっぱいの三角形」は頂点バッファを使わない定番の技です。頂点シェーダで vertex_index(0,1,2)だけから3頂点の座標を計算すると、画面を覆う大きな三角形になり、 はみ出す部分はラスタライザが自動で捨てます。

陰影(ヒルシェード): 法線と光から明るさを決める

標高の色だけだと、30mの細かい尾根や谷(斜面の向き)が見分けにくいので、地形の法線と固定の光源から明るさを求めて、頂点の色に掛けます。 表示メニューの「陰影表示」でON/OFFできます(既定はON。HillshadeState。18・19節)。

  • 法線: 頂点にnormal_xy(単位法線の東・北成分をsnorm16で4バイト。上向き成分はsqrt(1-x²-y²)でシェーダーが復元)を持たせる。 mesh.rsのnode_normalsが、隣のノードの位置の差(中心差分。縁や海に隣接するノードは片側差分)の外積から求める。 位置は丸める前のf64を使う(原点から遠いタイルでf32だと、隣との差が誤差に埋もれてざらつくため)
  • 光源: ENU座標で固定(北西から仰角45度)。カメラの向きに依らず、地図の陰影の一般的な向きになる。2D表示でも同じ
  • 明るさ: (AMBIENT + (1-AMBIENT)·max(n·L, 0)) / 平地の値(AMBIENT=0.35)。分母で正規化してあり、平地はちょうど1(色が変わらない)。光の側の斜面は約1.25倍、反対側は約0.43倍
  • 陰影を付けない頂点: 覆域ドーム・海に隣接して法線が求まらない点は、単位法線ではありえない値(UNLIT_NORMAL=xy成分の長さが1超)にして、シェーダーが見て掛けない。 x=y=0は「真上向き=平地」の正当な値なので、別の印が必要だった
sim3dview/src/terrain/terrain.wgsl(実際のコード、抜粋)const LIGHT_DIR = vec3<f32>(-0.5, 0.5, 0.70710678);  // 北西・仰角45度(ENU: 東,北,上)
const AMBIENT = 0.35;

fn hillshade(normal_xy: vec2<f32>) -> f32 {
    let xy2 = dot(normal_xy, normal_xy);
    if (xy2 > 1.0) { return 1.0; }            // UNLIT: 陰影なし
    let normal = vec3<f32>(normal_xy, sqrt(1.0 - xy2));
    let lambert = max(dot(normal, LIGHT_DIR), 0.0);
    let flat_level = AMBIENT + (1.0 - AMBIENT) * LIGHT_DIR.z;   // 平地の明るさ
    return (AMBIENT + (1.0 - AMBIENT) * lambert) / flat_level;
}
💡 なぜ頂点ごと・xy成分だけ?

明るさは法線について線形なので、頂点ごとに求めて面の内側を補間しても、法線を補間してから画素ごとに求めるのとほぼ同じ結果になります。 法線を3成分(12バイト)ではなくxyのsnorm16(4バイト)にしたのは、頂点が数千万個あるためです。snorm8では精度が足りず、緩い斜面で段差状の縞が出ます。

水域レイヤー: 地球そのものを、画素ごとに判定する

地形メッシュが張られない所(マスクファイルの水域・欠損タイル・タイル内のNODATA・地形データの範囲外)には、 WGS84楕円体の海抜0mの面を水色で描きます。この面は「地形メッシュが無い所から見える背景」として現れるだけなので、 水域の範囲を別に持つ必要はありません。

メッシュ方式(以前)

緯度経度の格子を楕円体上に張る。セルが弦になって、1度のセルで面が中央で約240m凹む。地形との継ぎ目、範囲の限り(遠景で途切れる)、深度の競合(z-fighting)が問題になった。

楕円体を直接判定(いま)

画面いっぱいの三角形1枚。各画素の視線と楕円体の交点をシェーダーで求める。丸みが厳密で、範囲の限りがなく、メッシュも要らない。

楕円体の式は、ENU座標の点pについて f(p) = c0 + 2 g·(M p) + |M p|²(f=0が楕円体の面)の形にしました。 Mは「ENUからECEFへの回転」と「半径で割る」を合わせた3×3行列、gは原点のECEF座標を半径で割ったものです。 原点は楕円体の上にあるので定数項がほぼ0になり、原点から遠い点でも桁落ちしません(ECEFの絶対座標約6.4e6mのままf32で二乗すると、数mの誤差になります)。 f≒2h/a(hは楕円体高)なので、この式が既存の座標変換と一致することを合成テストで確かめました(原点から約2,000kmの点でも、海抜0mで誤差0.1m以下)。

fn fs_water(in: DownsampleOutput) -> WaterOutput {
    // 画素の視線(カメラの基底から直接。逆VP行列はf32の誤差で向きがずれる)
    let origin = camera.eye.xyz + offset * (1.0 - perspective);
    let dir = camera.forward.xyz + offset * perspective;
    // f(origin + t·dir) = a t² + 2 half_b t + c = 0 を解く
    let disc = half_b * half_b - a * c;
    if (disc < 0.0) { discard; }                 // 楕円体に当たらない視線 = 空(黒のまま)
    /* 桁落ちしにくい解の公式で、手前の交点 t_near を求める */
    let hit = origin + dir * (t_near + WATER_DEPTH_MARGIN_M / length(dir));
    out.color = vec4<f32>(WATER_COLOR, 1.0);

}

水域は「深度を書く」: 水面越しに地形の裏側が透けないように

水域は、地形メッシュより先に描きます。当初は深度を書かず、地形が常に水域の上に上書きされる形にしていました。 標高0m以下の地形(DSMの負の値)が水域に隠れないようにするためでしたが、副作用がありました。 地球の丸みの向こう側にある陸地や、水面の下にある地形まで、水面越しに描かれてしまうのです (海面すれすれの低い視点から遠くを見ると、本来は地球に隠れるはずの陸地が海の中に透けて見えました)。

そこで、楕円体を不透明な地球本体として扱い、視線との交点の深度を書くようにしました。 ただし書く深度は、交点から視線に沿ってWATER_DEPTH_MARGIN_M(1,000m)奥へずらした点のものです。 地形は、交点から1km以内の奥までは水域より手前として描かれるので、標高が0m以下の地形が水域に隠れることはありません (標高-Hの地形と視線が角度θで交わるとき、交点との視線方向の距離はH/sinθ。-10mでもθが約0.6度以上なら隠れません)。 丸みの向こう側の地形は、水平線から数km以上奥なので、隠れます。

💡 ここも「近似で済ませない」

メッシュ方式でも、セルを細かくすれば見た目は近づきますが、「丸み」「継ぎ目」「範囲」「深度の競合」を全部近似で抱えることになります。 楕円体との交点は数式1つで厳密に求まるので、近似を持ち込まないほうが、コードも短く、破綻もしませんでした。 視線も、逆行列ではなくscreen_to_rayと同じカメラの基底から作っています(12節・15節の教訓と同じ)。

12 カメラ: 反転Zと視点操作

「地形の全体(数百km)から山肌(数百m)まで」を同じカメラで見るために必要な、深度バッファの工夫と、 視点操作の仕組みです。

深度バッファと「反転Z」

3D描画では、各画素で「どの三角形が手前か」を深度バッファに記録して判定します。 普通は手前(near)を0、奥(far)を1に写しますが、この写し方だと数値の精度がnear付近に偏り、 遠くでは隣り合う面の深度が同じ数値に丸められて、勝ち負けが不安定になります(z-fighting)。 Sim3dViewは近く(1m)から遠く(数千km)までを同じ画面に映すので、遠景で地表が透けたり、 カメラを動かすたびに模様が変わったりしました。

対策が反転Zです。近くを1、遠くを0に写すと、浮動小数点が「0に近いほど細かく表せる」性質と、 遠くほど深度が詰まる性質が打ち消し合い、どの距離でもほぼ一定の相対精度になります。 

sim3dview/src/terrain/camera.rs（実際のコード、抜粋）let proj = match self.projection {
    // nearとfarを「入れ替えて」渡すだけで反転Z(near→深度1, far→深度0)になる
    Projection::Perspective { fov_y_radians } =>
        directx::perspective(fov_y_radians, self.aspect, self.z_far, self.z_near),
    Projection::Orthographic { view_height_m } => {
        let (half_h, half_w) = (view_height_m * 0.5, view_height_m * 0.5 * self.aspect);
        directx::orthographic(-half_w, half_w, -half_h, half_h, self.z_far, self.z_near)
    }
};

レンダラー側の設定も揃える必要があります。深度バッファはDepth32Float、深度クリア値は0.0、 比較はGreater(値が大きい=手前が勝つ)です。ここを片方だけ変えると何も映らなくなります。

⚠️ 反転Zに触れるときは、ピッキングも一緒に

画面のクリック位置から視線(レイ)を求めるscreen_to_rayは、深度・射影と表裏の関係にあります。 反転Zを導入した時は、射影行列の逆変換で復元する部分が壊れて、地図の右クリックで緯度経度が取れなくなりました。 その後、ズームアウトを広げると、逆行列で復元した「近い2点の差」から向きを求める方式そのものが、f32の丸め誤差で破綻しました。 今はカメラの基底(前・右・上)と画角から直接視線を求めています(15節)。深度・射影を触るときは、必ずscreen_to_rayも見直します。

透視投影は、一度「遠方が無限遠」の特殊な行列(perspective_infinite_reverse)にしたところ、 原点から遠い地表の描画が省略される不具合が出たため、near・farとも有限の値に戻しました。 farは8,000kmで、最大ズームアウトの距離(2,000km)と、データの対角線(約4,000km)を含む大きさです (かつては背景の板の外周を覆うために10,000kmでした。15節)。 farを伸ばしても、精度を決めるのは主にnearなので、実地形の精度には影響しません。

OrbitCamera: 注視点のまわりを回る

カメラは「注視点(target)からの距離・水平角(yaw)・仰角(pitch)」の3つで決まる球面座標です。 ENUはZ-up(上がZ)なので、glamのlook_atの上方向にVec3::Zを明示して吸収します。

💡 「原点」と「中心点」は別物

原点(OriginState)は座標系そのものの基準で、サーバーが正の状態を持ち、 変えられるのはシミュレーション停止中だけです。中心点はカメラの注視点(target)で、 Shift+ドラッグで自由に動かせますが、動かしても原点・メッシュ・観測点は一切変わりません。 メニュー「表示 → 中心点を原点に戻す」は、targetを原点の真上(実際の地表標高)へ戻すだけです。

この「戻す」ボタンからTerrainViewへの通知は、RecenterRequestStateというカウンタのSignalで 行っています。ボタンは数を1増やすだけ、TerrainView側のEffectが増加を検知してtargetを戻します (0はまだ押されていない状態として無視)。「イベントを直接呼ぶ」代わりに「状態の変化として渡す」、 Leptosらしい疎結合の作り方です。

カメラは、地面の下にもぐらない

オービットカメラは注視点(地面の一点)のまわりを回るので、仰角を負にすると、視点が地面の下に入って地形の裏側が見えました。 また、視点の真下の地形が注視点より高い(尾根の陰・山の斜面)と、仰角が正でも視点が地面に埋まります。 そこで、注視点ではなく「視点の真下の地面の高さ」を基準に、視点を地面の上30mより下に行かせません(3Dモードのみ。2Dは視点の高さが見た目に関係しない)。

  1. まず距離を保ったまま仰角を上げる。ドラッグで下へ回すと、地面の高さで止まる操作感になる。仰角を変えると視点の水平位置も動き、真下の地面の高さも変わるので、数回繰り返して収束させる
  2. 仰角を最大まで上げても届かない(ズームインで近すぎる・注視点の周りが高い)ときは、視点を真上へ持ち上げ、注視点との距離と仰角をそこから求め直す(水平位置は変えない)
  3. 仰角が水平より下向き(注視点を見上げる)なのは許す。谷底から山頂を見上げる姿勢は、視点が地面の上にあるので
sim3dview/src/terrain/camera.rs（実際のコード、抜粋)/// ground_up(東, 北) は、その水平位置の地面のENU上座標(丸み込み)。camera.rs自体は地形を知らない
pub fn keep_above_ground(&mut self, ground_up: impl Fn(f32, f32) -> f32) {
    for _ in 0..6 {
        let eye = self.eye();
        let min_z = ground_up(eye.x, eye.y) + MIN_EYE_CLEARANCE_M;   // 30m
        if eye.z >= min_z { return; }
        let sin_pitch = (min_z - self.target.z) / self.distance;
        if sin_pitch >= MAX_PITCH.sin() { break; }              // 仰角を上げても届かない
        self.pitch = sin_pitch.asin().max(self.pitch).clamp(MIN_PITCH, MAX_PITCH);
    }
    /* 届かなかったら、視点を真上へ持ち上げて distance / pitch を求め直す */
}

13 見通し・覆域の計算

地図を右クリックで置いたレーダー観測点から、「どこまで見えるか」を地形の陰と 地球の丸みから計算します。これはsim3dviewライブラリの機能で、 計算はすべてブラウザ(Rust)の中で行います。

マスク角アルゴリズムと呼ばれる方法です。観測点から1方位ごとに1000点ぶん外へ進み、 各点の「見かけの仰角」を求めます。これまでの最大仰角以上なら見える点として距離を記録、 低ければ手前の地形の陰です。電波は空気の屈折でやや下向きに曲がるので、地球の半径を 4/3倍した仮想の球(等価地球半径)の上でまっすぐ進むとみなし、 距離dの地点はd² / (2 × 等価半径)だけ見かけ上沈むと計算します。 

sim3dview/src/terrain/los.rs（実際のコード、抜粋）const K_FACTOR: f64 = 4.0 / 3.0;   // 等価地球半径係数

const SAMPLES_PER_RAY: usize = 1000; // 1方位あたりのサンプル点(50km先で50m間隔)

fn curvature_drop_m(distance_m: f64, r_eff_m: f64) -> f64 {
    (distance_m * distance_m) / (2.0 * r_eff_m)
}

// compute_los の内側ループ

    }
}

3Dドームの高解像度化

ドームの解像度を決める要素は3つあります。方位の刻み(1mil)、1方位のサンプル数(1000点)、仰角リングの数です。 仰角リングは、7段(0/5/10/20/35/55/80度)から28段(0〜10度を1度刻み、10〜30度を2度刻み、以降35/40/45/50/60/70/80度)にしました。 地形に遮蔽されるのは低い仰角なので、そこを細かくしています。リング間の面は、方位を間引かず1mil刻みのまま三角形にします(面どうしは重ならないので、半透明の重なりによるちらつきは起きません)。 一方、最上段を1点に閉じる傘の部分だけは、細い三角形が1点へ大量に重なってちらつくので、160mil(9度)刻みに間引いたままです。 ドームは約100万頂点(約24MB)になりました(その後、38段・3200方位の描画で約71万頂点に。36.2節)。

尾根の見かけの仰角がリングの仰角に近い方角では、1mil(50km先で約50m)ごとの標高のわずかな差で、遮蔽の有無が入れ替わります。 その方位だけ遠くまで届く部分が、ドームの低い所に細い放射状の筋として目立つようになりました。データが正しく反映された結果ですが、 これは後で、方位方向の平滑化(メディアン→平均)で一時期目立たなくしていましたが、その平滑化は後日「やっぱりやめたい」という要望で撤去したので(36.6節)、いまはこの筋がそのまま見えます。

14.1 全タイルをチャンクで持つ(下限は620m)

全タイルを6×6のチャンクのメッシュで描き、チャンクごとに独立してレベル(L1〜L4)を選びます。 最も粗くてもL1(約617m/セル)で、遠いタイルもこれより粗くはしません。全390タイルのL1の分(下限)だけで、約1,520万頂点あります。 以前は、遠いタイルを「タイル全体を1枚のメッシュ(L0、約1.85km/セル、約4千頂点)」で描き、近づいてからチャンクに切り替えていました。 「距離に応じた解像度ではなく、全体的に同じ高解像度を保てないか」という要望から、下限を引き上げました (世界座標で全域を30mにすると約50億頂点で不可能。L1なら約1,500万頂点で現実的です)。

14.2 どの距離で、どのレベルになるのか

ルールは1つです。画面上で1セルが0.7ピクセル以下になる、最も粗いレベルを選ぶ(CHUNK_TARGET_CELL_PX = 0.7)。 1ピクセルが表す実寸は、透視投影なら 2 × 距離 × tan(縦画角/2) ÷ canvasの高さ です。遠いほど1ピクセルが大きい=粗いセルで足りる、という当たり前を式にしたものです。 描画は2倍スーパーサンプリングなので、1ピクセルは描画解像度では約2ピクセル分です。目標は2.0→1.0→0.7と下げてきました(小さいほど遠くまで細かいレベルを使います。1.0だと遠方が粗く、0.5だと近くの最細が予算で足りなくなるため0.7)。

fn ideal_level(data: &TerrainData, pixel_m: f32, from: usize) -> usize {
    let max_level = data.num_levels() - 1;
    (from..=max_level)
        .find(|&k| cell_size_m(data, k) <= CHUNK_TARGET_CELL_PX * pixel_m)
        .unwrap_or(max_level)
}

14.3 計画: plan_levels は「純粋関数」

plan_levelsは、カメラ・canvasの高さ・現在の状態を受け取り、各タイルをどう描くかを返すだけの関数です。 GPUにも通信にも触れないので、頭の中でも追いかけやすく、テストもしやすい形です。処理は次の順です。

  1. 距離と視野: タイル(と、必要ならチャンク)ごとに、基準位置から最も近い点までの距離と、視錐台に入るかを求める。 視野判定は「4隅と中心のクリップ座標が、同じ側の外にすべて出ていれば見えない」という簡易テスト(余裕20%)。 タイルの一番近い点でも下限のL1で足りるなら、そのタイルのどのチャンクも目標はL1なので、チャンクごとの距離・視錐台の計算を省く (全タイルがチャンクなので、遠くの多数のタイルで毎回計算すると重い)
  2. 全タイルがチャンク: 以前は、L0で足りるタイルはチャンクにせず1枚で描き、ヒステリシス(REVERT_MARGIN = 0.7)で行き来を防いでいた。下限をL1にしたので、この切り替えは廃止した。 視野の外は現状維持
  3. チャンクごとの目標レベル: 各チャンクの距離から理想のレベルを決める。ここでもヒステリシスで、「理想より1つだけ細かい現状」は下げない
  4. 予算の配分: チャンクの頂点の合計をDETAIL_VERTEX_BUDGET = 2,500万以下にする(下で詳しく)

頂点の予算: どこに配るか

描画の重さは、ほぼ頂点の総数で決まります。そこで「常駐する頂点の総数」に上限を設けました。 全タイルの下限(L1)が約1,520万頂点で、残りの約980万頂点を、近いチャンクを細かくするのに使います。合計最大およそ2,500万頂点で、 GPUメモリは頂点(28バイト)とインデックスで約1.2GBです(従来の単一メッシュは約420万頂点。予算は300万→600万→2,500万と増やしてきました)。

14.4 適用: update_lod は「少しずつ」進める

カメラが動くたびにメッシュを作り直すと重すぎるので、適用は次のように間引いて行います。

  • 2種類の予約: render_now(カメラ操作)からの予約(schedule_lod)は150msのデバウンスを通り、待っている間に来た予約は捨てる。ドラッグ中はさらに後回し(操作が止まってからやり直す)。一方、取得の完了・メッシュ反映の続きからの予約(schedule_lod_soon)は、8msだけ待って続ける(同じ瞬間に終わった複数の取得を1回にまとめる程度)。カメラ操作用のデバウンスを取得の補充にまで使うと、取得の合間が空いて全体が遅くなる
  • 段階的に細かくする: L4が欲しくてもまだ届いていなければ、取得済みの最も細かいレベルまでまず上げる。L1→L2→L3→L4と、届いた順に細かくなる。 最初のチャンク化には全チャンクのL1が要る(約69KBの小さなファイルを1つ取得)
  • 1回に作る量は、時間の目安で区切る(UPLOAD_TIME_BUDGET_MS = 12ms。頂点数の安全上限MAX_UPLOAD_VERTICES_PER_ROUND = 60万は、次の1個の重さを予測できないための保険として残す): 1個進めるたびに経過時間を見て、目安を超えたら残りはすぐ次の更新(8ms後)へ回す。1個は必ず進める(0個だと終わらない)。時間で区切るので、速い端末は1回で多く進み、遅い端末は自動で細かく刻まれて、画面が固まらない。以前は「1回60万頂点+150ms待ち」で、全タイルのL1(約1,280万頂点)だけで約21回=約3.2秒の下限があった。起動後は、全タイルがL1に上がるまでこの更新が続く(同じPCで約3秒)
  • 更新後の後始末: 地形の高さが変わるので、注視点の高さ(ズームしても地面に埋まらないように)と、地表に貼り付いた観測点・覆域を合わせ直す

sim3dview/src/terrain/fetch.rs(実際のコード、抜粋)/// チャンク1個分のグリッドを、タイルファイルからHTTP Rangeで取得する。
pub async fn fetch_chunk_grid(base_url: &str, key: TileKey, level: usize,
                              chunk: usize, chunk_cells: usize) -> Result<Vec<i16>, String> {
    let url = format!("{base_url}/tiles/L{level}/{}.bin", tile_name(key));
    // レコードは固定サイズなので、バイト位置は計算で決まる
    let record_bytes = (chunk_cells + 1) * (chunk_cells + 1) * 2;
    let start = chunk * record_bytes;
    let bytes = fetch_binary(&url, Some((start, start + record_bytes - 1))).await?;
    if bytes.len() != record_bytes { /* サイズ不一致はエラー */ }
    Ok(decode_i16_le(&bytes))
}

サーバー側(C++)は、単一範囲のRange: bytes=a-bを解釈して206 Partial ContentとContent-Rangeを返します(7節)。 もしサーバーがRangeを無視して全体(200)を返しても、クライアントが必要な範囲を切り出すので動きますが、毎回26MBを転送することになります。

  • 同時取得は16件まで、同じものは重複させない。失敗したものは記録して、延々と再試行しない。取得が終わるたびに、デバウンスなしで次を補充する(14.4節)。全タイルのL1(約69KBが390個)を起動後に取得するので、6件だと約1分かかっていた。1件の所要は中央値11msなので、ブラウザの同一ホストへのHTTP/1.1接続(通常6本)を、16件で埋められる。390件の取得は、補充が周期的だった頃は約5.3秒、いまは約2.2秒(同じPC上)
  • キャッシュ: 取得したグリッドは合計300MBまで残す。超えたら、いま画面に出していないものから、最後に使った順に古いものを捨てる(画面に出しているものは絶対に捨てない)
  • HTTPキャッシュ: 上のメモリのキャッシュとは別に、ブラウザ自身が地形ファイルを保存する。サーバーがETagとCache-Control: no-cacheを付けるので、2回目以降は確認だけで済み、転送はほぼゼロになる(7節)
  • 安全性: サーバーはlevel・nameを英数字・_・.だけに制限し、..を含むものは400で拒否する(パストラバーサル対策)

14.10 画面の外のメッシュは描かない(視錐台カリング)

14.11 レベルの切り替えを、なめらかにする(クロスフェード)

ここまでの仕組みでは、チャンクのレベルが変わる(カメラの動き・取得の完了)たびに、古いメッシュを消して新しいメッシュに一瞬で差し替えていました。 細かさや陰影(法線が細かいほど、ヒルシェードの濃淡が細かくなる)の違いが一度に切り替わるので、レベルの境目が目立ちます。 そこで、古いメッシュを350msだけ残し、新旧を混ぜながら入れ替えるようにしました(FADE_DURATION_MS)。

半透明ではなく、画素ごとの「疎密」で混ぜる

素直な混ぜ方は、新旧を半透明で重ねることです。でも半透明は、描く順に依存し、深度を書けず、奥のメッシュが透けます(覆域ドームで苦労したのと同じです。36節)。 そこでディザを使います。画素ごとに0〜1の値(dither_noise。画素の位置から求める、隣どうしで値が散るパターン)を出し、 新しい側は「値 < 割合」の画素だけ、古い側は「残りの画素」だけを描きます(discard)。 どちらか一方しか描かないので、不透明のままで、深度は普通に書け、描く順にも依存せず、新旧が同じ画素で深度を奪い合うこともありません。 

sim3dview/src/terrain/terrain.wgsl(実際のコード、抜粋)// メッシュごとの値は、instance_indexで引く表に入れる。x: 表示する画素の割合、y: 1なら反転(古い側)
@vertex
fn vs_fade(in: VertexInput, @builtin(instance_index) instance: u32) -> FadeVertexOutput {
    let base = shade_vertex(in);
    var out: FadeVertexOutput;
    out.clip_position = base.clip_position;
    out.color = base.color;
    out.fade = fades.entries[instance].xy;
    return out;
}

@fragment
fn fs_fade(in: FadeVertexOutput) -> @location(0) vec4<f32> {
    let noise = dither_noise(in.clip_position.xy);   // 画素の位置から0〜1の疎密のパターン
    // 新しい側は noise < 割合 の画素、古い側は残りの画素
    let is_new = noise < in.fade.x;
    let inverted = in.fade.y > 0.5;
    if (is_new == inverted) { discard; }
    return vec4<f32>(in.color, 1.0);
}
🔧 C++erの視点

ゲームの世界ではスクリーンドア透明(stipple)やディザ透明と呼ばれる古典的な技で、LODの切り替え(LODのディザ・フェード)にもよく使われます。 discardは「この画素は描かない」という指示で、C++でいえばcontinueに近いものです。ただしdiscardを含むシェーダーはGPUが早期の深度テストで画素を捨てにくくなるので、 切り替え中のメッシュだけ専用のパイプライン(terrain_fade)で描き、普段の地形(terrain)には使いません。

const ORTHO_DEPTH_RANGE_M: f32 = 1_200_000.0;

高度を下げて範囲を広げる(カメラを地表に近づけ、奥行きを1,300kmにした)ことで、全域が収まります。正射影の深度は距離に対して線形なので、 範囲を広げても精度の悪化は緩やかです(透視投影の反転Zの話は12節)。

15.3 クリックした場所を、丸みごと正しく求める

地図をクリックして緯度経度を得る(右クリックで観測点、原点の指定)処理は、視線(レイ)を地形に向かって少しずつ進め、地表と交わる点を探します(レイマーチング)。 ズームアウトの上限を広げたら、遠くから見ると別の場所を拾うようになりました。原因は3つ重なっていました。

① 視線の向きの計算誤差

以前のscreen_to_rayは、逆行列で「nearの点」と「途中の点(nearの約2倍=約1m先)」を復元し、その差を向きにしていました。 カメラが数千km離れると座標が10⁶のオーダーになり、f32の丸め誤差(0.1m超)が1mの差に対して大きすぎ、向きが大きくずれます。

② 標高そのものと比べていた

視線の高さを「標高」と比べていましたが、メッシュの頂点は丸みで下がったENUの上座標です。 原点から離れるほど、比べる相手がずれます。

③ 緯度経度への逆変換が近似

EnuTransform::inverseは原点の近くだけで成り立つ接平面近似で、2,000km離れると数十kmずれます。

直し方は3つに対応します。

sim3dview/src/terrain/camera.rs(実際のコード、抜粋)// ① 視線はカメラの基底(前・右・上)と画角から直接求める(逆行列を使わない)
let forward = (self.target - self.eye).normalize();
let right = forward.cross(self.up).normalize();
let up = right.cross(forward);
match self.projection {
    Projection::Perspective { fov_y_radians } => {
        let half_h = (fov_y_radians * 0.5).tan();
        let half_w = half_h * self.aspect;
        (self.eye, forward + right * (ndc_x * half_w) + up * (ndc_y * half_h))
    }
    /* 正射影: 原点を画面の位置だけずらし、向きは forward のまま */
}
sim3dview/src/terrain/heightmap.rs(実際のコード、抜粋)/// ENUの水平位置(東, 北)の真上/真下にある地表点の(緯度, 経度, ENU上座標)。
/// 「上座標を仮定→測地座標へ戻す→その地点の地表の上座標で更新」を数回繰り返して求める。
pub fn ground_at_enu(data: &TerrainData, transform: &EnuTransform, east: f64, north: f64)
    -> (f64, f64, f32)
{
    // 丸みによる低下量の第一近似を初期値にする(0から始めるより収束が速い)
    let mut up = -(east * east + north * north) / (2.0 * transform.ellipsoid_params().0);
    let mut lat_lon = (0.0, 0.0);
    for _ in 0..4 {
        let (lat, lon, _h) = transform.enu_to_geodetic(east, north, up);   // ③ 厳密な逆変換
        let elevation = sample_heightmap(data, lat, lon).unwrap_or(0.0);
        up = transform.transform_f64(lat, lon, elevation as f64)[2];       // ② ENUの上座標
        lat_lon = (lat, lon);
    }
    (lat_lon.0, lat_lon.1, up as f32)
}
  • ③ enu_to_geodeticは、ENU→ECEF(原点の回転行列の転置)→測地座標(反復法)の厳密な逆変換です。inverse(近似)は断面図など原点の近くだけで使います
  • マーチングの高速化: 視線の高さが最高標高より上にある間は、交差しえないので地表の評価を省略します。刻みは約1.3km、最大8,000kmまで進めます
  • 検証: 往復変換(ENU⇄測地)と、丸みの沈み量(石垣島で約300km前後)の単体テストを書きました。実機では、朝鮮半島・本州中部を3D/2Dでクリックして、その地域の緯度経度が返ることを確認しています

ライブラリに入っているもの

  • 地形の取得・共有 — TerrainStore
  • 3D/2D地形ビュー — TerrainView(回転・ズーム・パン・右クリック)
  • 地形LOD — 全域で620m以上、近づくほど細かく(最細は元データの30m)。自動(14節)
  • 陰影(ヒルシェード) — 尾根や谷が見える。HillshadeStateでON/OFF(11節)
  • 水域レイヤー — 海抜0mの楕円体を水色で。地球の丸みに沿い、地形は隠さない(11節)
  • 座標系と原点 — OriginState・EnuTransform・OriginDialog・OriginPickState(地図クリックで指定)

  • 航跡表示 — TracksState。航空機・艦船・車両などの位置を、向きつきシンボル・ラベル・航跡・高度線で(38節)
  • 断面図 — CrossSectionView
  • 右クリックメニュー — ContextMenu・MapMenuState。項目は使う側が決める(26.7節)
  • 汎用UI部品 — TabbedPanel・FloatingPanel(モーダル/動かせるウインドウ。28.5節)
  • 内部の計算(標高・座標変換・見通し・レンダラー) — 部品が使うが、アプリからは呼べない(非公開。6.6節)

ライブラリに入っていないもの

  • 通信(WebSocket・msgpack・URLの決定)
  • VAB・状況パネル・メニューバー・全体レイアウト
  • 物体の位置を受け取る通信(位置はTracksState::setで渡す。描画・ラベル・航跡はライブラリ側にある。38節)
  • 観測点・原点・カメラの永続化(リロードで消える)
  • サーバー(地形ファイルを配信する側)

20 データ契約と自前データの作り方

ライブラリが読むのは、次の4種類のファイルです。形式を満たせば、ALOSでなくても、前処理ツールを使わなくても動きます。 (以前は2ファイルでしたが、地形LODのために「タイルごとの多段解像度」の形になりました。9節・14節)

ファイル(ベースURLの下)いつ取得中身
/metadata.json起動時範囲・標高の最小最大・楕円体・レベル定義・チャンク分割数
/tile_index.json起動時存在するタイルの一覧
/base.bin起動時(全部)レベル0(タイル全体で1枚)を全タイル分連結したもの
/tiles/L{k}/N035E138.bin(k=1以上)ズームしたとき、必要な分だけレベルkのタイル別ファイル(チャンクのレコードを連結)

metadata.json

フィールド型意味
tile_levels整数の配列レベルごとの、1度タイル1辺あたりのセル数(先頭がレベル0=最粗)。2要素以上必要で、レベル1以降はchunks_per_tileで割り切れること
chunks_per_tile整数1度タイルの一辺を何チャンクに分けるか(現在は6)。レベル1以上のグリッドが対象
elevation_min, elevation_max数値elevation_maxは色ランプの上端と、クリック判定の高速化(視線が最高標高より上なら地表を調べない)に使う。実際の最大(海を除く)にする。下限は色では使われない(0m固定)
geodetic_bounds{min_lat, max_lat, min_lon, max_lon}全タイルの外接矩形(整数度)。原点入力の範囲チェックにも、サーバーの範囲チェックにも使われる
ellipsoid{a_m, inv_f}楕円体(GRS80なら 6378137 と 298.257222101)

上記以外のフィールド(出典CRSのメモなど)を足しても、読み込み側は無視します。旧形式のwidth/heightは廃止されました。

tile_index.json

tile_index.json{ "tiles": [
    { "lat": 35, "lon": 138, "elevation_min": 0, "elevation_max": 3776 },
    ...
] }

lat/lonはタイルの南西角の整数度です。陸のないタイルは含めません(含まれないタイルは、標高0mの海として扱われます)。 並びの順がbase.binの並びと一致している必要があります(i番目のタイルが、base.binのi番目のグリッド)。

グリッドの形式(base.bin と tiles/…)

  • ノード数は(N+1)×(N+1)(Nは、そのグリッドの一辺のセル数)。値はリトルエンディアンのint16(標高メートル)。データなし・海は-32768
  • 並びは行優先で、南→北・西→東(最初の行が最南端)。北→南が標準のGeoTIFF系ツールとは逆なので注意
  • base.bin: レベル0(N = tile_levels[0])のグリッドを、タイルごとに連結。全体のサイズは タイル数 × (N+1)² × 2 バイトで、合わないと「size mismatch」で失敗します
  • tiles/L{k}/…: N = tile_levels[k]、c = N ÷ chunks_per_tile。チャンク(番号 = 行(南→北)×分割数+列(西→東))ごとに (c+1)²個のノードを、番号順に連結。 チャンク(cx, cy)のノード(i, j)は、タイル全体の(cx·c + i, cy·c + j)番目のノードに当たり、 緯度 = lat_tile + (cy·c + j) / N、経度 = lon_tile + (cx·c + i) / N。隣のチャンクと縁のノードは同じ値にします(継ぎ目が一致する)
  • ファイル名はN035E138.binの形式(N/S + 緯度3桁、E/W + 経度3桁)

配信の条件

  • ベースURLの下に上の4種類を返す(末尾スラッシュなしのベースURLを渡す)
  • ブラウザのページと別オリジンなら、Access-Control-Allow-Originを付ける(サンプルのC++サーバーは*)
  • HTTP Range(Range: bytes=a-b、単一範囲)に対応するのを強く推奨: 細かいレベル(L3・L4)は、チャンク1個ぶんだけをRangeで取得します。 未対応(Rangeを無視して全体を返す)でも、クライアントが必要な範囲を切り出すので動きますが、毎回タイル1枚ぶん(L4で約26MB)を転送します
  • ETagとCache-Control: no-cacheを付けるのを推奨: ブラウザが保存した応答を、変更がなければ304で再利用でき、2回目以降の表示で数十MBを取り直さずに済みます(サンプルのC++サーバーは、ファイルの大きさ+更新時刻をETagにしています。7節)。有効期限(max-age)は、データを作り直したときに古い地形が残るので付けないほうが安全です

手を動かして試す: 合成地形を作る

前処理ツールもGeoTIFFも無しで、動作確認できる小さな地形(1度タイル1枚、中央に1500mの丘、南西の角だけ「海」)を作るPythonスクリプトです。 レベル0(60セル)と、チャンクで持つレベル1(180セル)の2レベルだけを作ります(LODは2レベル以上が前提。14節)。 できたファイルを好きなHTTPサーバーで配信し、そのURLをTerrainStore::newに渡せば表示できます。 

make_terrain.py(出力サイズと構造をローダーの期待に照合済み)import json, math, os, struct

TILE_LAT, TILE_LON = 35, 139        # 1度タイル1枚(南西角)
LEVELS = [60, 180]                  # L0=タイル全体で1枚 / L1=6x6のチャンクで持つ細かいレベル
K = 6                               # 1度タイルの一辺を何チャンクに分けるか
NODATA = -32768                     # データなし(海)


def height(lat, lon):               # 中央に1500mの丘
    x = (lon - (TILE_LON + 0.5)) * 2
    y = (lat - (TILE_LAT + 0.5)) * 2
    return 1500.0 * math.exp(-(x * x + y * y) * 4)


def node(i, j, n):                  # タイルをn分割したときのノード(i: 西→東, j: 南→北)
    if i == 0 and j == 0:
        return NODATA               # 例: 南西の角を「海」にする
    return round(height(TILE_LAT + j / n, TILE_LON + i / n))


os.makedirs("tiles/L1", exist_ok=True)

# レベル0: (N+1)^2 ノードを、行=南→北・列=西→東の順に並べる(base.bin)
n0 = LEVELS[0]
grid0 = [node(i, j, n0) for j in range(n0 + 1) for i in range(n0 + 1)]
with open("base.bin", "wb") as f:
    f.write(struct.pack(f"<{len(grid0)}h", *grid0))          # リトルエンディアンのint16

# レベル1: チャンク(行=南→北, 列=西→東の順)ごとの (c+1)^2 ノードを連結。縁のノードは隣と共有する
n1 = LEVELS[1]
c = n1 // K                                                   # チャンク1辺のセル数
records = []
for cy in range(K):
    for cx in range(K):
        for j in range(c + 1):
            for i in range(c + 1):
                records.append(node(cx * c + i, cy * c + j, n1))
with open("tiles/L1/N035E139.bin", "wb") as f:                # 名前は N/S+緯度3桁, E/W+経度3桁
    f.write(struct.pack(f"<{len(records)}h", *records))

real = [v for v in grid0 if v != NODATA]
with open("tile_index.json", "w") as f:
    json.dump({"tiles": [{"lat": TILE_LAT, "lon": TILE_LON,
                          "elevation_min": min(real), "elevation_max": max(real)}]}, f)
with open("metadata.json", "w") as f:
    json.dump({
        "tile_levels": LEVELS, "chunks_per_tile": K,
        "elevation_min": min(real), "elevation_max": max(real),
        "geodetic_bounds": {"min_lat": TILE_LAT, "max_lat": TILE_LAT + 1,
                            "min_lon": TILE_LON, "max_lon": TILE_LON + 1},
        "ellipsoid": {"a_m": 6378137.0, "inv_f": 298.257222101},
        "has_texture": False,
        "default_origin": {"lat_deg": 35.5, "lon_deg": 139.5},
    }, f, indent=2)

実行して確認したこと: base.binが7,442バイト(61²×2)、tiles/L1/N035E139.binが69,192バイト(36×31²×2)で、 実データの同じレベルのファイルとサイズが一致すること。チャンクの並びで引いたレベル1の標高が、レベル0の補間値と平均0.3m差で整合すること。 (ブラウザで表示するところまでは、この合成データでは試していません)

ALOS DSMのGeoTIFFから作るなら、tools/geotiff_preprocess(9節)を使います。 独自のデータソースを使う場合は、上のスクリプトのheightを差し替えるだけで、 残りの部分(タイル・チャンクの並べ方、メタデータの作り方)はそのまま使えます。

カメラの初期距離(400km)とズームの範囲(100m〜2,000km)は、30度四方のデータを想定した固定値です。 上の1度タイルの例だと、初期表示では地形が小さく見えるので、ホイールでズームインしてください。

  • 航跡のシンボル・ラベルは重なりを避けません。ラベルはHTML要素なので、地形の陰に隠れても消えず、数百を超えるトラックでは要素の数が先に問題になります(38.7)
  • 作図の半透明の太い折れ線は、つなぎ目の重なりでアルファが二重に掛かり、濃く見えます。Viewの図形の大きさはメートルなので、縦長の画面では視野に入る位置が変わります(37節)
  • 覆域の3D/2D表示は選択中の観測点1つだけ。断面図だけは全観測点を合算します
  • 水域の面は海抜0m固定で、ON/OFFも色の変更もできません(湖の水面が実際の標高にあっても、水域は海抜0mに描かれます)。標高が0m以下の地形が水域に隠れないのは、水域が深度を1km奥へずらして書くためで、ほぼ水平の見え方では限界があります(11節)
  • 観測点・カメラ・原点は永続化されません(リロードで初期化)
  • 原点は地形の範囲内にある前提です(範囲チェックはUIと、サンプルサーバーの防御的チェックの役目)
  • CSR(ブラウザ描画)専用です。SSR(サーバー側描画)には対応しません
  • 初期カメラ距離・ズーム範囲は30度四方向けの固定値(20節)

36.1 四角い枠から、画面サイズ固定の「ピン」へ

以前のマーカーは、地表に置いた一辺約8kmの四角い枠(線)でした。広域では小さく、近づくと巨大になって、肝心の「観測点はここ」が分かりにくい形でした。 いまは先端が観測点のピンです。選択中は黄色、それ以外はオレンジで、縁取りと中の点が付きます(26.3節の画像)。

この「位置は3D、大きさは画面」を実現するのがビルボードです。頂点はpositionにアンカー(観測点の3D位置)を持ち、 aux.xyに「アンカーから画面上で何px離すか」を持ちます。頂点シェーダーがアンカーを射影して、そのぶんだけずらします。

36.2 3Dドームをなめらかに

実機で、ドームがなめらかに見えない原因は3つありました。

  1. 半径の丸め誤差。遮蔽のない方角なのに、高い仰角のリングほど半径が不揃いでした。compute_los_domeは水平距離を50m刻み(最大観測範囲÷1000)に丸め、それをcos(仰角)で割ってスラントレンジにします。 丸め方が仰角ごとに違うので、下の図のようにリングごとに最大約190m(87度なら約320m)の凸凹が出ていました。
  2. 1方位だけの遮蔽。1mil(0.056度)ごとに独立に判定するので、1方位だけ遮蔽される所が「観測点へ向かう細い三角形」になり、放射状の筋に見えました(13節の警告)。
  3. 上空のリング間隔。最大10度刻みで、輪郭が多角形に見えました。

対策は次のとおりです。

  • 上限までは丸めない: 遮蔽されずに上限(最大観測範囲×cos仰角)まで届いたリングは、サンプル位置ではなく上限ちょうどを返す(los.rsのfinalize)。
  • 頂点を間引く: 計算は4mil刻み(1,600方位)。面を張るときは2方位に1つにし、さらに高いリングほど間引く(円周が短いので、1/cos(仰角)以下の2のべき乗個おき。最大32)。 間引きの違うリングの間は、上のリングの1辺に下のリングの複数の頂点を扇状につなぐ(stitch_rings)ので、すき間もT字の継ぎ目もできません。
  • リングを増やす: 28段→38段(0〜10度は1度刻み、〜30度は2度、〜60度は3度、以降は4度刻みで最上段は87度)。
  • 半径の平滑化は、しません。一時期は方位方向(メディアン→平均)・仰角方向(隣のリングと[1,2,1]/4)の平滑化を入れていましたが、「覆域データの平滑化はやっぱりやめにしたい」という要望で撤去しました(36.6節)。 1方位だけ遮蔽される所は、観測点へ向かう細い三角形(放射状の筋)としてそのまま出ます。

sim3dview/src/terrain/markers.rs(実際のコード、抜粋)// 隣り合う2リングの間の帯。下のリングの頂点が多い分は、上の1辺に複数の三角形を扇状に付ける
fn stitch_rings<V: Copy>(lower: &[V], upper: &[V], mut push: impl FnMut(V, V, V)) {
    let ratio = lower.len() / upper.len();
    for j in 0..upper.len() {
        let (u0, u1) = (upper[j], upper[(j + 1) % upper.len()]);
        for i in 0..ratio {
            push(lower[j * ratio + i], lower[(j * ratio + i + 1) % lower.len()], u0);
        }
        push(u0, u1, lower[((j + 1) * ratio) % lower.len()]);   // 上の辺を閉じる
    }
}

36.3 2Dの覆域が、まだらに欠けていた理由

2Dの覆域は、観測点を中心に、境界上の隣り合う2点へ扇形の三角形を並べて塗ります(13節)。各頂点の高さは「その地点の地表+20m」ですが、 三角形の中は一直線の平面です。観測点と境界の間には数km〜数十kmの起伏があるので、平面が地形に埋まる所ができます。 以前はこの塗りを、他の描画と同じ深度テストありで描いていたため、地形が手前にある部分で塗りが隠れ、場所によって欠けて見えました。

真上から見る2Dは、地形に隠れる物が無いので、深度テストそのものが不要です。塗りも輪郭線もDrawVertexにして、 深度テストなしのパイプライン(draw_screen_pipelineを絶対座標のuniformで使う)で、地形の上に重ねます。 あわせて次も変えました。

  • 輪郭線を太さ2.5pxの太い線(37節)に。境界はそのまま(平滑化なし)。
  • 塗りの不透明度を0.22→0.32に。半透明の緑が地図の上で読み取れる濃さにした。
  • 観測点のピン(36.1)は、この覆域のあとに描く。ピンが覆域の塗りの下に隠れない。
⚠️ 観測点が山頂だと、低い高度の覆域は空になる

上の画像は、観測点が富士山の山頂近くにあるので、覆域の海抜高度を6,000mにしています。既定の1,000mでは、観測点(約3,800m)より低い高度の対象は、 すぐ足元の斜面に遮られるので、覆域は空になります(物理的に正しい結果です)。「覆域が出ない」ときは、まず高度設定(28節)を疑ってください。

低い高度の2D覆域は、境界がギザギザになる(いまは平滑化しない)

覆域の海抜高度を低く(たとえば50m)すると、島や岩の陰が、観測点から放射状に伸びる細い楔になり、境界と塗りがギザギザに見えます (高度1,000mでは、ほぼ円で気にならない)。以前はここもドームと同じ角度の幅で平滑化していました(メディアン±2・平均±6を2回)が、 「覆域データの平滑化はやっぱりやめにしたい」という要望で撤去しました(36.6節)。いまはLosPointの生の水平距離をそのまま境界に使うので、 低い高度ではこのギザギザがそのまま出ます。

2Dの重さは、36.5節の変更ですでに解消していました。開発ビルドの実機で、2Dのズーム・パンの固まりは、覆域なしのときと同じ約50〜110ms、 観測点の追加や覆域高度の変更は約70〜100msです(覆域が原因の固まりは、なくなっています)。

36.4 地面すれすれで、シンボルの下半分が埋まる: ビルボードの深度

高度0mの船(SHIP1)のシンボルが、カメラを浅い角度に倒すと、下半分だけ水面に隠れて欠けることが分かりました。 地上車両も、地形に沿って似た欠け方をします。原因はビルボードの深度です。ビルボードは画面サイズ固定の四角形で、頂点は同じ深度(足元1点の深度)を持ちます。 画面で足元より下の画素は、視線がもっと手前で地面や水面に当たるので、その深度がシンボルより手前になって、地面が勝ちます。36.1節の「距離の0.2%だけ手前へ」では、浅い角度ほど足りません。 (水面は交点より1km奥へずらした深度を書きますが、それでも足元の画素の水面はシンボルより手前です。)

そこで、頂点ごとに足元を通る局所の水平面を考え、その画素の視線が面に当たる点の深度までは、シンボルを手前へ寄せます(billboard_depth)。 面の上の点が、画面でずれた位置に射影される条件は、同次座標が線形なので2×2の連立一次方程式になり、遠近の近似なしで厳密に解けます(逆行列は使いません)。 面に当たらない・視点の後ろなら、深度は足元のままです。シンボル・選択の輪・観測点のピンに共通で効きます。 

sim3dview/src/terrain/draw.wgsl(実際のコード、抜粋)fn billboard_depth(anchor: vec3<f32>, c: vec4<f32>, offset_ndc: vec2<f32>) -> f32 {
    let depth = c.z / c.w;
    // 足元の局所の「真上」(地球の中心とアンカーを結ぶ向き)と、その面の2方向
    let up = normalize(anchor + vec3<f32>(0.0, 0.0, EARTH_RADIUS_M));
    let east = normalize(cross(vec3<f32>(0.0, 1.0, 0.0), up));
    let north = cross(up, east);
    let m1 = u.view_proj * vec4<f32>(east, 0.0);    // 面の上でeastへ1m進んだときのクリップ座標の変化
    let m2 = u.view_proj * vec4<f32>(north, 0.0);
    // 面の点 anchor + s*east + r*north が、画面で offset_ndc だけずれた位置に射影される条件は
    // s, r の連立一次方程式(同次座標は線形なので、遠近の近似なしで厳密に解ける)
    let t = c.xy / c.w + offset_ndc;
    let a11 = m1.x - t.x * m1.w;  let a12 = m2.x - t.x * m2.w;
    let a21 = m1.y - t.y * m1.w;  let a22 = m2.y - t.y * m2.w;
    let b = offset_ndc * c.w;
    let det = a11 * a22 - a12 * a21;
    let s = (b.x * a22 - a12 * b.y) / det;
    let r = (a11 * b.y - a21 * b.x) / det;
    let hit = c + m1 * s + m2 * r;                    // 視線が面に当たる点のクリップ座標
    let hit_depth = hit.z / hit.w;
    // 手前(反転Zでは大きい方)を採る。寄せすぎないよう上限は深度の1.3倍
    return max(depth, min(hit_depth, depth * BILLBOARD_PLANE_MAX_PUSH));
}
  • 寄せすぎない: 視線が地面とほぼ水平だと、画素がわずかに違うだけで、視線が面に当たる位置は視点側へ大きく動きます。それに合わせて寄せ続けると、手前の山に隠れるはずのシンボルまで、山の上に描かれてしまいます。 そこで寄せる量は深度の1.3倍までにしています(BILLBOARD_PLANE_MAX_PUSH)。
  • 面より手前の起伏には、従来どおり隠れる: 寄せるのは足元の水平面までなので、その手前に立つ本物の山には隠れます。
  • 地球の丸み: 面の向きは、アンカーと地球の中心(ENUの原点の−R)を結ぶ向きで見積もります(球で十分です)。遠方でも、面が地表と同じ向きになります。
⚠️ 確かめるときの落とし穴: 水平線の向こうは、隠れて正しい

最初の再現では、視点が地表すれすれ(ほぼ水平)で、船は水平線の向こう(地球の丸みの陰)にありました。そのときシンボルの上端だけが空に出るのは、物理的に正しい姿です。 「埋まる」の確認は、水平線の内側(視点をやや高くして、船が水面の上に見えるくらい)の角度で、修正の前後を同じカメラで比べます。実際にそうして、修正前は下半分が欠け、修正後は全体が見えることを確かめました。

36.5 覆域を出している間の操作を、重くしない

覆域を出したままズームやカメラ操作をすると、画面が固まりました。開発ビルドで測ると、観測点を追加すると約2秒、覆域を出したままズームすると約1.05秒の固まりが10秒間に22回でした (観測点なしでは固まりなし)。計測には、MessageChannelのメッセージの間隔を使いました(setIntervalは、非表示のペインだと約1秒に間引かれるので、最初の計測は無効でした)。

原因は2つです。(1)覆域の計算(6400方位×1000サンプル=640万回の標高補間)を、毎回同期で全部やっていた。 (2)地形のレベルが切り替わる(14.4節のchanged)たびに、覆域を作り直していた。だからズームやカメラ操作でLODが動くたびに、約1秒固まりました。 極座標図(見通し範囲タブ)も、同期で計算していました。

対策中身
小分けにして非同期で進める計算を再開できる形(RangeComputation・DomeComputationのadvance(data, count))にし、UIが8msずつ進めて、合間に描画・入力に処理を譲る(run_in_slices)。新しい要求が来たら、古い計算は世代(generation)が変わって止まる。極座標図も同じ方式
結果をキャッシュキー(CoverageKey)が同じなら、計算せずジオメトリの作り直しだけ。原点変更・選択し直し・観測点の範囲の外のチャンクの切り替えでは、計算しない
地形の変化は少し待つレベルの切り替えで計算し直すときは、300ms待ってまとめる(切り替えは続けて何度も起きる)。計算が終わるまでは、地形だけが変わったなら前の覆域を出し続け、観測点・モード・高度が変わったなら消す
方位を間引くドーム1,600方位(4mil)、2D覆域3,200方位(2mil)、極座標図3,200方位。間引いた結果は、全方位の結果の同じ方位の値と一致する(テストで確認)。小分けにしても結果は変わらない(これもテスト)
 
sim3dview/src/ui/util.rs(実際のコード)// 重い計算を小分けにして進める。stepは少しだけ進めて、終わったらtrueを返す関数
pub async fn run_in_slices(mut step: impl FnMut() -> bool, cancelled: impl Fn() -> bool) -> bool {
    loop {
        let start = js_sys::Date::now();
        loop {
            if cancelled() { return false; }      // 結果が要らなくなった(世代が変わった)
            if step() { return true; }
            if js_sys::Date::now() - start >= SLICE_BUDGET_MS { break; }   // 8ms使ったら
        }
        gloo_timers::future::TimeoutFuture::new(0).await;   // 描画・入力に処理を譲る
    }
}

キャッシュのキーに含める「地形」は、観測点の最大観測範囲(緯度経度の範囲)に重なるチャンクの、レベルの組のハッシュです(terrain_signature)。標高のサンプリング結果が変わるのは、 その範囲のチャンクのレベルが変わったときだけなので、遠くのチャンクが切り替わっても、計算し直しません。

struct CoverageKey {
    marker: RadarMarker,

36.6 平滑化を撤去した話

36.2節(ドーム)・36.3節(2D覆域)には、しばらくの間、方位ごとの半径の並びをメディアン → 平均でなだらかにする平滑化が入っていました (地形の細かい凹凸や1方位だけの遮蔽が、観測点へ向かう細い三角形・放射状の筋に見えるのを消すため)。道具立ては「円環のメディアン (median_circular)でトゲを消してから、円環の平均(mean_circular)を2回重ねて段差を曲線にする」(smooth_circular) +「ドームは仰角方向にも、隣のリングと[1,2,1]/4で平均する」(smooth_across_rings)というものでした。

その後、「覆域データの平滑化はやっぱりやめにしたい」という要望を受けて、3Dドーム・2D境界とも平滑化を撤去しました。 dome_geometry・coverage_2d_geometryは、計算結果(DomeRing・LosPointのrange_m)を 平滑化せずそのまま頂点に使います。smooth_circular・median_circular・mean_circular・smooth_across_rings・ smooth_dome_rangesと、対応する定数(DOME_SMOOTH_*・DOME_ELEVATION_SMOOTH_PASSES・COVERAGE_SMOOTH_*)は terrain::markersから削除しています。

平滑化以外の対策——半径の丸め誤差の修正(36.2節)、リング数を増やして最上部まで細かくすること、方位の間引きとring_strideによる 高いリングの追加間引き、stitch_ringsによる継ぎ目のないつなぎ、覆域の計算の小分け・キャッシュ(36.5節)——は、そのまま残っています。 撤去したのは「計算結果の値をなだらかにする」処理だけです。

💡 結果として戻るもの

地形の細かい凹凸や、1方位(4mil)だけ遮蔽される所が作る、観測点へ向かう細い放射状の筋(ドーム)や、低い高度での境界のギザギザ(2D覆域)は、 平滑化する前の生の計算結果のとおりに戻ります。遮蔽されない方角の半径(最大観測範囲)は、平滑化があってもなくても変わりません。

単体テスト: 平滑化専用だった5件(smoothing_keeps_constant_and_removes_single_spikes・smoothing_wraps_around_and_softens_steps・ mean_passes_round_a_step_into_a_smoother_curve・coverage_boundary_smoothing_rounds_narrow_wedges_but_keeps_wide_shadows・ ring_smoothing_keeps_constants_and_softens_steps_between_rings)を削除し、残りのテスト(間引き・帯のつなぎ目・色・ピン形状など)が 変更なしで通ることを確認しました。

36.7 複数の覆域を、同時に出す

覆域(3Dドーム・2D領域)は、以前は選択中の観測点1つだけでした。いまは、見通し範囲タブの「すべての観測点の覆域を同時に表示」(RadarMarkersState::show_all_coverage。既定はOFF)をONにすると、 すべての観測点の覆域が同時に出ます。OFFなら、これまでどおり選択中の1つです。

観測点ごとに、計算・キャッシュ・頂点を持つ

36.5節の仕組み(小分けの非同期計算・キャッシュ・世代による取り消し)を、観測点ごと(MarkerCoverage)に持たせました。GPUへは、表示する観測点の頂点をつないで1つのバッファとして載せます(sync_gpu)。 観測点が増えても計算は独立に小分けで進み、計算済みの観測点は計算し直しません(たとえば3つ目を足しても、1つ目・2つ目のキャッシュはそのまま)。 

sim3dview/src/ui/terrain_view/coverage.rs(実際のコード、抜粋)// 観測点1つぶんの覆域の状態
struct MarkerCoverage {

    built: Option<BuiltGeometry>,      // 頂点(キーとメッシュ原点つき)
    pending: Option<CoverageKey>,      // 計算中のキー
    generation: u64,                   // 古い計算を止めるための世代
}

pub(super) struct CoverageState {
    markers: HashMap<u64, MarkerCoverage>,           // 観測点のid → 状態
    visible: Vec<u64>,                               // 表示する観測点(表示の順)

    if parts == s.coverage.uploaded { return; }

  • 削除された観測点の状態は捨てる: 観測点の一覧から消えたら、その状態(キャッシュ・頂点)を捨てる。進行中の計算は、状態がなくなっているので、結果を捨てる。
  • モードが違うものは載せない: 3Dはドームの頂点、2Dは領域の頂点だけを集める。モードを切り替えると、観測点ごとに、そのモードの計算(未計算なら)を始める。

観測点ごとに色を変える

同じ色で重ねると、どの覆域がどの観測点か分かりません。そこで、観測点のidで色を選びます(coverage_colors(id)。6色のパレットで、7番目からは最初に戻る)。 1番目の観測点は、これまでどおり(ドームが水色・2Dが緑)です。2Dの輪郭線の色は、塗りの色を白へ寄せた不透明色です。一覧の各行には、その色の見本(左=3D、右=2D)が付きます。

観測点色(左=3Dドーム、右=2D覆域)
1番目(id 1, 7, …) 水色 / 緑
2番目(id 2, 8, …) 桃色 / 橙
3番目(id 3, 9, …) 黄 / 青
4番目(id 4, 10, …) 黄緑 / 桃
5番目(id 5, 11, …) 橙 / 水色
6番目(id 6, 12, …) 紫 / 黄

頂点数は、表示する観測点の数に比例します(ドームは1観測点あたり約16万頂点)。また、半透明のドームは重なる所で濃くなり、色の違うドームどうしの重なりは、描く順(観測点の一覧の順)でわずかに見え方が変わります (同じ色のドームは順序に依存しませんでしたが、色が違うので、厳密には依存します)。多数の観測点を同時に出すなら、選択中だけに戻すのが軽くて見やすい使い方です。

実機で、観測点を2つ置いて「すべて」をONにすると、3Dでは水色と紫の2つのドームが、2Dでは緑と橙の2つの領域が同時に出て、固まりはありませんでした(開発ビルド)。

37 作図: 図形・線を、絶対座標かカメラに固定して描く

アプリが任意の図形・線を地図上に出すための汎用機能です(terrain::drawing)。円・矩形・多角形・扇形・球・直方体・円柱・円錐・折れ線を、 塗り・枠線・不透明度つきで描けます。絶対座標に固定するか、カメラに固定するかを選べるのが特徴です。

37.3 高度の基準: 水平な面か、地形に貼り付くか

貼り付く面は、地形の起伏に沿うよう細かく分割します(辺500m・輪郭250m。海抜の水平な面は辺20km・輪郭2km)。三角形の数は面積から上限を決めているので、 大きな図形でも頂点が増えすぎません。地表に貼り付けたものは、地形メッシュ(粗いLODを含む)とのZファイティングを避けるため、地表より15m持ち上げます。 3D図形のAboveGroundは、位置の真下の地表を基準に置くだけで、図形は変形しません。

37.4 太い線: 頂点シェーダーが画面のpx幅に広げる

WebGPUの線プリミティブは太さ1pxしかありません。そこで線分1本を四角形(三角形2枚)にして、頂点シェーダーが画面のピクセル幅へ広げます。 面も線も同じ頂点形式(DrawVertex、56バイト)・同じパイプラインなので、塗りも枠線も1つのバッファにまとまります。 

sim3dview/src/terrain/draw.wgsl(実際のコード、抜粋)// 画面のピクセル単位で、線の向き(反対側→この端点)と、その左手の法線を求める。
let half = u.viewport.xy * 0.5;
let pa = a.xy / a.w * half;
let pb = b.xy / b.w * half;
var dir = normalize(pa - pb);
let normal = vec2<f32>(-dir.y, dir.x);
let half_width = 0.5 * width_px;
// 幅方向に±半幅、端点は線の向きへ半幅だけ延ばす(折れ線のつなぎ目の隙間を埋める)。
let offset_px = normal * (in.params.y * half_width) + dir * half_width;
let ndc = a.xy / a.w + offset_px / half;
out.clip_position = vec4<f32>(ndc * a.w, z, a.w);
  • カメラの後ろ: 透視投影では、視点の後ろの点を画面へ射影すると向きが反転して帯が壊れます。端点のクリップ空間のwが0.5より小さければ、線分をそこで打ち切ります。
  • 面との深度: 線は同じ位置の面と同じ深度になってZファイティングを起こすので、クリップ空間のzを相対的に手前へ寄せます(LINE_DEPTH_BIAS)。
  • 制約: 半透明の太い折れ線は、つなぎ目の重なり部分だけアルファが二重に掛かって濃く見えます(不透明なら出ません)。

37.5 描画パス: カメラ固定は、2つ目のパスで描く

ViewとScreenを地形と同じパスで描くと、地形の深度に隠されてしまいます。そこで、カメラ固定のものが1つでもあるときだけ、2つ目のレンダーパスで描きます。 1つ目のMSAAカラーをLoadで引き継ぎ、深度だけClearし直すので、地形とは隠し合いません。

Viewの座標は、ビュー行列を掛けず射影行列だけ(Camera::projection_matrix)で射影します(カメラから見た座標=右・上・前方が、そのまま射影される)。 Screenは、ピクセル座標をクリップ空間へ写す行列(深度は一定)を使います。2Dモード(正射影)でも同じです。 この3種類は、それぞれ別のuniform(view_proj)を持つだけで、同じシェーダーで描きます。

38 航跡表示: シミュレーションの位置を、シンボルで見せる

シミュレーション側から受け取った航空機・艦船・車両などの現在位置を、向きつきのシンボル・ラベル・航跡(軌跡)・高度線で表示します。 ライブラリは通信を知りません。アプリが受信のたびに「全トラックの最新状態」を渡すだけで、表示が更新されます(terrain::tracks)。

38.1 全体の流れ

38.2 メッセージ: TrackList(0x07)

サーバー→ブラウザの7つ目のメッセージです。全トラックの最新状態をまとめて送ります(差分ではない)。消えたトラックは、次の一覧から抜けるだけで済みます。 フィールドの並び順をC++とRustで一致させる決まりは、ここでも同じです(5節)。

38.3 サーバー側のデモシナリオ(Simulation)

デフォルト原点(富士山の近く)のまわりに、種別・所属の違う7つのトラックを楕円軌道で周回させます。位置はシミュレーション時刻tの関数なので、 状態を持たず、一時停止・再開しても矛盾しません。実際のシミュレータでは、この部分を、自分のシミュレーション結果からTrackを作る処理に置き換えます。

38.4 フロント側: 受信して、ライブラリへ渡す

ws.rsがTrackListをデコードしてsignals.track_listに入れ、track_bridge.rsのEffectが、 ライブラリのTrackへ変換してTracksState::setへ渡します。原点のミラー(OriginState)と同じ形の「橋渡し」で、 通信を知らないライブラリと、プロトコルを知るアプリの境目がここです。 

sample/sim_frontend/src/track_bridge.rs(実際のコード、抜粋)// 受信した1トラックを、ライブラリの表示用Trackへ変換する(値の意味はprotocol.hppのenumと一致)
fn to_library_track(t: &protocol::Track) -> Track {
    Track {
        id: u64::from(t.id),
        kind: match t.kind { 1 => SymbolKind::Aircraft, 2 => SymbolKind::Helicopter, 3 => SymbolKind::Ship,
                             4 => SymbolKind::Vehicle, 5 => SymbolKind::Missile, _ => SymbolKind::Unknown },
        affiliation: match t.affiliation { 1 => Affiliation::Friendly, 2 => Affiliation::Hostile,
                                           3 => Affiliation::Neutral, _ => Affiliation::Unknown },
        label: t.label.clone(),
        lat_deg: t.lat_deg,
        lon_deg: t.lon_deg,
        altitude: if t.alt_ref == 1 { Altitude::AboveGround(t.alt_m) } else { Altitude::Msl(t.alt_m) },
        heading_deg: t.heading_deg,
        speed_mps: t.speed_mps,
        pitch_deg: t.pitch_deg,
        roll_deg: t.roll_deg,
    }
}

// サーバーから届くTrackListをTracksStateへ反映するEffect。一覧は毎回「全トラックの最新状態」なので、そのまま置き換える
pub fn bridge_tracks(signals: WsSignals, tracks: TracksState) {
    Effect::new(move |_| {
        if let Some(list) = signals.track_list.get() {
            tracks.set(list.tracks.iter().map(to_library_track).collect());
        }
    });
}

TracksState::set(Vec<Track>)は、前回に無かったIDを新規、今回に無いIDを削除として扱います。航跡(過去の位置)は、同じIDの間だけ貯まります。 前回の位置が航跡の最後の点から250m以上離れていれば足し(上限400点)、動かない間は増やしません。

38.5 シンボル: 向きつきビルボード

種別ごとの形は、「進行方向が上・その右が+x」の座標のポリゴンで持ち、耳切り法(37節の多角形と同じ関数)で三角形にします。 縁取り(暗色、1.3倍)→本体(所属の色)の順に重ねます。

38.7 自分のシミュレータにつなぐ

  1. サーバー: 自分のシミュレーション結果からprotocol::Trackを作り、TrackListに詰める。idは実体ごとに固定する。
  2. 配信: 好きな頻度でencode_frame(MsgType::TrackList, list)を全員へ送る。接続直後にも1回送る。
  3. フロント: protocol.rsに同じ順序の型を書く(配列位置で対応するので、並び順は完全に一致させる)。
  4. 橋渡し: track_bridge.rsのようにTrackへ変換して、TracksState::setへ渡す。別のプロトコル(REST・gRPC-Webなど)なら、ここだけが変わります。

表示の切り替えは、TracksStateのshow_labels・show_trails・show_altitude_lines(RwSignal<bool>、既定ON)です。 sampleでは、表示メニューの「航跡ラベル/航跡(軌跡)/高度線」がこれを切り替えます。

⚠️ いまの制約

トラックが密集すると、シンボルやラベルが重なります(重なりの回避は未実装)。ラベルは画面へ射影した位置に置くだけで、地形の陰に隠れても消えません (シンボルは深度テストで隠れますが、ラベルは隠れません)。トラックの数が数百を超える使い方では、ラベルのHTML要素の数が先に問題になります。

38.8 3Dモデル(glTF)で描く(おまけ機能)

シンボルの代わりに、3Dモデルを地図に置く機能です。C++でいえば、ゲームエンジンに「メッシュを読み込んで、位置と向きを与えて描く」処理を足したようなもので、 地形・作図・航跡の描画とは責任を分けてあります。使うのはglTF 2.0のGLB(1ファイルに形・材質・バッファを詰めたバイナリ)。Unityの標準はFBXですが、FBXは独自形式で WebAssemblyから読みにくいので、BlenderなどでGLBへ書き出して使います。Rustのgltfクレートが読み込みを担当します。

GLBを読む

import_glbは、GLBの三角形メッシュの位置・法線・頂点色・材質の基本色を取り出し、シーンの全ノードの変換(親から子へ掛けた行列)を頂点へ焼き込んで、1つのメッシュにまとめます。 テクスチャ・アニメーション・スキンは対応しません(画像のデコードが要らないので、gltfクレートはimageを引かない設定で使います)。 座標は、glTFの規約(+Y上・+Z前)から、ライブラリの機体座標(x=右・y=前・z=上。東・北・上と同じ右手系)へ回します。

向き: ヘディング・ピッチ・ロール

terrain/models/placement.rs(抜粋)// 機体座標→ENU座標の回転。frameは、その地点の東・北・上(EnuTransform::local_frame)
pub(crate) fn attitude(frame: [[f32; 3]; 3], heading_deg: f32, pitch_deg: f32, roll_deg: f32) -> Mat3 {
    let local = Mat3::from_rotation_z(-heading_deg.to_radians())   // ヘディング: 北から時計回り
        * Mat3::from_rotation_x(pitch_deg.to_radians())            // ピッチ: 機首上げが正
        * Mat3::from_rotation_y(roll_deg.to_radians());           // ロール: 右翼が下がるのが正
    Mat3::from_cols(frame[0].into(), frame[1].into(), frame[2].into()) * local
}

ポイントはframeです。地球は丸いので、原点から離れた地点の「上」は、原点の「上」(0,0,1)から傾きます(原点から1,000kmで約9度)。 そこで、その地点の東・北・上をECEFから求めて、原点基準のENUの成分で持ちます(EnuTransform::local_frame)。地平線近くの遠い機体も、その場所の水平に沿って傾きます。

描く

モデルは不透明で、深度を書き、作図の不透明な図形と同じ位置(覆域ドームより前)で描きます。頂点バッファが2本(頂点・インスタンス)なので、パイプラインはmodel_batchの中で作りました。 同じモデルは、機数ぶんをインスタンス描画(1回のdraw_indexed)で描き、インスタンスごとの違い(変換行列・所属の色)はModelInstanceで渡します。 陰影は頂点ごとのランバート(環境光+光源1つ)、所属の色を35%混ぜます。

第10部・まとめ

39 設計パターンと落とし穴

このコードベースに繰り返し出てくる、持ち帰り価値の高い考え方と、実際に踏んだ落とし穴です。

① 低頻度Config + 高頻度Values

VabConfig/StatusPanelConfig(構造の定義、接続時のみ)と SimState(数値だけ、毎フレーム)を分離。構造が変わらない限り、 同じ情報を毎フレーム再送しない。

② サーバーを正とする状態

原点(OriginState)はC++側だけが保持し、UIは常に配信された値の「写し」を表示する。 クライアントが複数いても状態がズレない。

③ 拒否は必ず理由付きで返す

コマンドを黙って無視せずCommandErrorを返す。要求元にだけ返す (broadcastしない)ことで、他クライアントの画面を無関係なエラーで汚さない。

④ 受信は積む、適用は1箇所で

マルチスレッドの世界で状態を書き換える権利を1スレッドだけに絞る (7節のコマンドキュー)。UI側のWsConnectionも同じ発想で 接続状態をひとつのInnerに集約している。

⑤ ライブラリは「窓口」だけを公開する

通信・URLを知らないライブラリが、contextの型(TerrainStore・OriginState)だけを 窓口にする。アプリ側で翻訳するEffectを1つ書けば、プロトコルを差し替えてもライブラリは無傷(6節)。

⑥ 「揃ったら動く」冪等な初期化

非同期に完了する複数の条件は、どちらの完了イベントからも同じtry_initを呼び、 揃っていなければ何もせず戻る。順序を仮定しない(8節)。

⑦ 見ている所だけ細かく(LOD)

全部を細かく持つのをやめ、粗いデータを常駐させて、近くだけ細かいデータを取りに行く。 頂点数には「予算」を置き、近い順に配る(14節)。データの単位を、タイルからさらにチャンクへ細かくしたのも同じ発想。

⑧ 描く物と、問い合わせる物を一致させる

標高の問い合わせを「いま画面に出しているレベル」で引く。見た目と計算が食い違うと、観測点が浮くなどの不整合が出る(14.6)。 呼び出し側を変えずに済んだのは、問い合わせの入口がsample_heightmap1か所だったから。

⑨ 「全件を渡す」窓口

DrawingState・TracksStateは、差分ではなく最新の全体を受け取る。IDの対応づけ・航跡の蓄積・消えたものの片付けは、ライブラリが持つ。 送る側(サーバー・橋渡し)は「いまの全部」を作るだけで済み、取りこぼした更新で状態がずれない(38節)。

⑩ 位置は3D、大きさと向きは画面(ビルボード)

ピン・シンボルは、頂点に「アンカー(3D)+画面のpxのずれ(+進行方向)」だけを持たせ、射影後の合成は頂点シェーダーに任せる。 カメラを動かしても頂点バッファに触らずに済み、ズームしても大きさが変わらない(36.1・38.5)。

⑪ 編集の途中は、本物と同じ部品で「仮の要素」として見せる

作成中の図形も、選択中の枠も、専用の描画を作らず、DrawingStateに仮の1要素として置いて更新する。既存の描画パスがそのまま使え、見た目も本物と食い違わない。 代わりに、更新のたびに全体の再構築が走るので、頻度(カーソル移動)は1フレームに1回へまとめる(37.7)。

⑫ 見せる側は「場所」を渡し、「項目」は使う側が作る

右クリックメニューは、ライブラリが右クリックした場所(MapMenuTarget)を求めて渡し、項目(何が起きるか)はアプリのコールバックが返す。 ライブラリは、レーダーや原点をどう扱うかを知らずに済む。FloatingPanel・OriginPickStateと同じ形(26.7)。

過去に踏んだ落とし穴

Leptosのview!の属性値

属性値に演算子を含む式を直接書かない。letで受けてから渡す(隣の属性が誤認識される)。

クロージャのSend境界

{move || ...}のようなchildren位置のクロージャはSendを要求し、 Rc<RefCell<..>>を直接捕捉できない。WsConnectionのような接続は、 StoredValue::new_localで包んだCopyのハンドル(サンプルのWsHandle)にして捕まえる。unsafe impl Sendは使わない。

CSSは「宣言順」で決まる

同じ詳細度のクラスは、後ろに宣言した方が勝つ。VABの.vab-button-activeは .vab-button-dummyより後ろに置く。

ライブラリ側だけ編集したら

path依存先はtrunkが自動でwatchしない。sim3dviewだけを直したら trunk serveを再起動する(sample側のファイルをtouchして再ビルドさせてもよい)。

広域では、近似と丸め誤差が壊れる

数千km離れると、f32の逆行列から向きを求める・接平面近似で緯度経度に戻す・標高そのものと視線を比べる、がすべて破綻する。 カメラの基底から直接求める、厳密な逆変換を使う、ENUの上座標と比べる、で直す(15節)。

水域が深度を書かないと、水面越しに透ける

「地形が水域に隠れない」ために深度を書かないと、地球の丸みの向こう側や水面の下の地形まで水面越しに描かれる。 楕円体を不透明な地球本体として深度を書き、地形には視線に沿って1kmの余裕を与える(11節)。

計測は、ペインが見えている状態で

Browserペインが非表示だと、setTimeoutが約1秒に間引かれて所要時間が常に約1000msになり、スクリーンショットも1つ前の描画のことがある。 計測はMessageChannelで完了を待ち、操作後は撮り直す。

範囲をコードに直書きしない

サーバーの範囲チェックが古い5度四方の固定値で、データを広げたら石垣島を拒否した。 データが持つ範囲(metadata.json)を読む(7節)。

モーダルだと、地図をクリックできない

FloatingPanelの既定は背景全体を覆うモーダル。地図をクリックして使うエディタを入れると、地図に届かない。 modal=falseで、透明な層(pointer-events: none)の上にウインドウだけがクリックを受ける形にした(28.5)。

メニューの位置は、描いてから測って直す

画面の端にはみ出すかどうかは、大きさを測らないと分からない。描画後にrequestAnimationFrameで測って収め、それまではvisibility: hiddenで隠す。 ブラウザペインはrequestAnimationFrameが遅い(約400ms)ので、確認するときは1.5秒ほど待たないと、補正前の位置を見てしまう(26.7)。
